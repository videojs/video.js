What is a guide? In this context, it's a document in the docs that's not an API reference. For API references, see <DocsLink slug="writing-style/write-references">Write reference pages</DocsLink>.

<Aside type="tip">
Oh hey by the way. A lot of this knowledge is encoded in the `write-docs` and `review-docs` Claude skills. You should still read it, but, now your LLM can help you along the way, too.
</Aside>

## 1. Understand our documentation structure

First, read and understand [Diátaxis](https://diataxis.fr/). We organize documentation into three modes:

1. **Concept pages** (`src/content/docs/guides/`): Explain a reusable mental model — design rationale, trade-offs, and context that helps readers with several tasks. Diátaxis calls this mode "explanation." If the background matters to only one outcome, keep it in that how-to instead.
2. **How-to guides** (`src/content/docs/guides/`): Help the reader achieve a specific outcome — one page per thing they want to do (Autoplay, Play live streams, Self-host the player). Address a real goal, assume competence, and include only the explanation needed to complete or adapt the task.
3. **Reference pages** (`src/content/docs/reference/components/` and `src/content/docs/reference/api/`): Describe exact machinery — components, features, hooks, utilities, options, state, and error codes. Most API surfaces use `write-api-reference` and the api-docs-builder; legacy error-code pages render the `video.js/errors` registry. See <DocsLink slug="writing-style/write-references">Write reference pages</DocsLink> for details.

<Aside type="note">
Diátaxis has a fourth mode — learning-oriented **tutorials**. We don't have a tutorials section yet — something we've intentionally chosen to omit, for now.
</Aside>

Concept pages and how-to guides share one folder and one URL prefix, `guides/`. The difference is the shape of the page, not its address. Reference has its own folder for exact API and error-code descriptions. The site derives that split from the path and shows it in the eyebrow above the title (for example "Guide › Playback").

A unit test, `pnpm -F site test diataxis`, guards the line between the two folders: no title starts with "How to", and no reference page carries how-to sections or a `<CustomUiNote />`. Whether a guide reads as a concept or a how-to is a judgement you make while writing and reviewing, with the compass below. The test helps by printing, as warnings only, any heading on a Concepts-section page that opens with a task verb such as "Add" or "Configure".

To pick a mode, use the Diátaxis [compass](https://diataxis.fr/compass/). Ask two questions: does the content inform **action** (practical steps) or **cognition** (understanding)? And does it serve the reader's **study** (acquiring skills) or their **work** (applying them)?

| | Informs action | Informs cognition |
|---|---|---|
| **Serves work** | How-to guide | Reference page |
| **Serves study** | How-to guide (Getting started) | Concept page |

Start with the reader's question:

- "How do I achieve this outcome?" belongs in a how-to guide.
- "Why does Video.js work this way, and when does that matter?" belongs in a concept page when the answer applies to several tasks.
- "What exactly does this export, prop, attribute, state field, or event do?" belongs in reference.

A capability does not automatically need its own guide. Keep a small task as a section of the broader outcome it serves, and keep exhaustive option lists in reference. Use this table to decide between concepts and how-tos:

| Concept page | How-to guide |
|---|---|
| Background shared by many guides | One specific goal |
| One concept per page | One outcome per page |
| Scannable, minimal prose | Working code up front |
| No prerequisites | Has prerequisites |
| Jump in anywhere | Read top to bottom |

Keep each page's job clear. A how-to guide leads with working code and includes only the explanation a reader needs to modify it — that's its "How it works" section. Deeper background belongs in a concept page; link to it instead of explaining inline. Step-by-step instructions creeping into a concept page belong in a how-to guide.

### How-to guide template

Give a topic its own guide when developers search for it by name, browser or platform rules affect it, and it takes several APIs explained together. Otherwise it stays a section of a broader guide (chapters live in Show captions and subtitles, not a guide of their own).

Most how-to guides use the same sections, in this order:

1. **Summary** — one or two sentences, no heading. Follow it with `<CustomUiNote />`, the shared note that tells pre-built-skin users the skin handles this and the guide is for building your own UI.
2. **Recommended approach** — the one way we recommend building it, smallest complete example first. Primary examples are real demo files imported into MDX, not inline fences.
3. **How it works** — only the background needed to understand or modify the code above, using exact exported names.
4. **Availability and constraints** — browser restrictions, platform differences, permission or user-interaction requirements, expected failure modes. Said plainly, not buried in asides.
5. **Common variations** — alternatives, kept separate so they don't blend into the recommended approach.
6. **Troubleshooting** — symptom, likely cause, fix.
7. **Related components**, **Related API**, **Related guides** — three link groups.

A guide may skip a section that doesn't apply. Established guides may keep a topic-specific structure when it tells the story more clearly — especially broad customization workflows such as Build your own UI component. Do not reorganize a useful page only to satisfy the template.

One goal per page. Titles are goal-oriented and in the reader's words: each completes the sentence "How to…" without the literal prefix ("Play live streams", "Show captions and subtitles" — not "Live Playback" or "Text Tracks"). Think about what someone who only knows YouTube — or their coding agent — would search for. One page should fully answer one question.

## 2. Create a guide in the correct content folder

Our guides are [MDX](https://mdxjs.com) files placed in the matching directory:

- Concept pages and how-to guides both go in `src/content/docs/guides/[slug].mdx`
- Reference pages go in `src/content/docs/reference/components/` or `src/content/docs/reference/api/`

Every guide needs a frontmatter block with `title` and `description`:

```yaml
---
title: 'Your guide title'
description: 'One-sentence summary for search and metadata'
---
```

There is no `type` field: the folder decides it, and a hand-written value would be ignored. Optional frontmatter fields:

- **`frameworkTitle`** — override the title for specific frameworks (e.g., `frameworkTitle: { react: 'Hooks in React' }`)
- **`ogTitle`** — shorter title for the default `/og/...` and `/og/twitter/...` social preview images. Use this when your page title is too long for the rendered OG card (over ~80 characters).

## 3. Add that guide to the sidebar

Next, open `src/docs.config.ts` and add your guide to the appropriate section of the sidebar. For example, to add a how-to guide on "Writing guides", you would add:

```ts
{
  slug: 'writing-style/write-guides'
}
```

The sidebar label defaults to the guide's `title` frontmatter; override it with `sidebarLabel`. If you want the guide to only apply to specific frameworks, you can specify that as well:

```ts
{
  slug: 'writing-style/write-guides',
  sidebarLabel: 'Writing guides',
  frameworks: ['react'] // Only for React
}
```

When a page changes slug, keep its old address alive with a rule in `site/netlify.toml`. Add one for the page and one for its `.md` twin, using `:framework` so a single rule covers every framework, and place them above the section-wide rules so a page that changed section as well lands in one hop:

```toml
[[redirects]]
  from = "/docs/framework/:framework/concepts/security"
  to = "/docs/framework/:framework/guides/content-security-policy"
  status = 301
```

A page does not have to appear in the sidebar. Set `hidden: true` on its entry to keep it reachable by URL and in search without a link, or leave it out of the sidebar entirely when it only needs to exist at an address you hand out.

### Why the sidebar has no folders

Each section lists its pages flat, and the section switcher at the top of the sidebar is the only level above them. Nested folders were removed on purpose: they hid pages behind a click, so readers scanning for a topic could not see it, and remembering which folders were open across navigations cost more code than it earned. A flat list of up to fifteen or so pages scans faster than a tree. If a section outgrows one screen, split it into two sections rather than nesting; if the pages inside naturally group, order them so the groups sit together.

<Aside type="note">
There is no `styles` restriction on sidebar items. Style is a client-side preference — every guide renders for all styles. To show style-specific content, use `<StyleCase>` within the guide, as shown below.
</Aside>

## 4. Follow our writing style

Keep documentation clear, human, and useful. Here are the key rules:

- **Sentence case for headings** — capitalize only the first word and proper nouns (e.g., "Choose your JS framework", not "Choose Your JS Framework")
- **Active voice, second person** — speak directly to the reader with "you"
- **Collaborative pronouns** — use "we," "us," and "our" when talking about the project or team
- **Avoid gerunds in headings** — prefer "Write good headings" over "Writing good headings"
- **Oxford comma** — always use the serial comma in lists of three or more
- **Gender-neutral language** — use "they" or "their" instead of "his" or "her"
- **Cut filler words** — remove "In order to," "basically," "simply," "might," "could," "perhaps"
- **Be precise** — make claims as strong as possible without becoming false; avoid vague qualifiers like "somewhat" or "fairly"
- **Read it out loud** — if it sounds awkward, rewrite it

## 5. Understand MDX and our components

### `<FrameworkCase>` and `<StyleCase>`
First, understand that the guide you write will be rendered for every framework / style combination (e.g., HTML + CSS, React + CSS) unless you restrict it to specific frameworks in the sidebar config as shown above.

Use the `<FrameworkCase>` and `<StyleCase>` components to conditionally show content to just one framework or style. `<FrameworkCase>` resolves at build time, so content for other frameworks is left out of the page entirely. `<StyleCase>` follows the reader's style preference, so its content is rendered for every style and shown or hidden with CSS:

```mdx
<FrameworkCase frameworks={["react"]}>
  React-only content
</FrameworkCase>
```

### Code annotations

You can annotate code blocks with special comments to highlight, diff, focus, or word-highlight specific lines. The annotation comments are stripped from the rendered output (and from copy/paste).

#### Diff

Show added and removed lines with `// [!code ++]` and `// [!code --]`:

```ts
function greet(name: string) {
  console.log('Hello') // [!code --]
  console.log(`Hello, ${name}!`) // [!code ++]
  console.log(`It's great to meet you.`) // [!code ++]
}
```

#### Focus

Dim everything except the focused lines with `// [!code focus]`. Hovering the code block reveals all lines:

```ts
function greet(name: string) {
  const message = `hello, ${name}!`
  console.log(message) // [!code focus]
}
```

#### Word highlight

Highlight a specific word or phrase with `// [!code word:term]`. For example, `// [!code word:name]` looks like this:

```ts
// [!code word:name]
function greet(name: string) {
  console.log(`hello, ${name}!`)
}
```

### `<ServerCode />`, for showing code from a `{variable}` or `?raw` imported file

While MDX supports inline variables like `{someVariable}`, this doesn't work inside of markdown code blocks.
If you tried
````mdx
```tsx
{someVariable}
```
````
You would just get
```tsx
{someVariable}
```

To work around this, use `<ServerCode />` instead of triple backticks.

<Aside type="caution">
Unlike regular markdown code blocks, which are automatically wrapped in a `<CodeFrame>` as described above, `<ServerCode>` renders a bare `<pre>` with **no** frame. You should use `TabsRoot` with a single `TabsPanel` to make it look pretty.
</Aside>

```mdx
import componentCode from '@/examples/react/Component.tsx?raw';
import { TabsRoot, TabsList, TabsPanel, Tab } from '@/components/Tabs';
import ServerCode from '@/components/Code/ServerCode.astro';

<TabsRoot client:idle>
  <TabsList client:idle label="Component implementation">
    <Tab client:idle value="component" initial>Component</Tab>
  </TabsList>
  <TabsPanel client:idle value="component" initial>
    <ServerCode code={componentCode} lang="tsx" />
  </TabsPanel>
</TabsRoot>
```

Which will happily render

<TabsRoot client:idle>
  <TabsList client:idle label="Component implementation">
    <Tab client:idle value="component" initial>Component</Tab>
  </TabsList>
  <TabsPanel client:idle value="component" initial>
    <ServerCode code={`import React from 'react';

function Component() {
  return <div>Hello, world!</div>;
}`} lang="tsx" />
  </TabsPanel>
</TabsRoot>

### `<Demo>`, for a live preview with tabbed source code

Use `<Demo>` to show a live, interactive example alongside the code that produces it. This is the standard pattern on reference pages (e.g., <DocsLink slug="reference/components/play-button">PlayButton</DocsLink>).

Pass the source files via the `files` prop — each entry has a `title`, `code` (a `?raw` import), and `lang` — and place the rendered demo in the default slot. Any `css` file in `files` is automatically scoped to the demo, so the demo's styles won't leak into the page.

Demos are framework-specific, so wrap each variant in `<FrameworkCase>` (and `<StyleCase>`, if applicable):

```mdx
import Demo from '@/components/docs/demos/Demo.astro';
import BasicUsageDemoReact from '@/components/docs/demos/play-button/react/css/BasicUsage';
import basicUsageReactTsx from '@/components/docs/demos/play-button/react/css/BasicUsage.tsx?raw';
import basicUsageReactCss from '@/components/docs/demos/play-button/react/css/BasicUsage.css?raw';

<FrameworkCase frameworks={["react"]}>
  <StyleCase styles={["css"]}>
    <Demo files={[
      { title: "App.tsx", code: basicUsageReactTsx, lang: "tsx" },
      { title: "App.css", code: basicUsageReactCss, lang: "css" },
    ]}>
      <BasicUsageDemoReact client:idle />
    </Demo>
  </StyleCase>
</FrameworkCase>
```

Which renders as:

<FrameworkCase frameworks={["react"]}>
  <StyleCase styles={["css"]}>
    <Demo files={[
      { title: "App.tsx", code: basicUsageReactTsx, lang: "tsx" },
      { title: "App.css", code: basicUsageReactCss, lang: "css" },
    ]}>
      <BasicUsageDemoReact client:idle />
    </Demo>
  </StyleCase>
</FrameworkCase>

<FrameworkCase frameworks={["html"]}>

### `<TabsRoot>` supports arbitrary content, too

You can place any old content underneath `<TabsPanel>`, and it'll show alongside whatever tabbed content you're showing. This is a pattern we've used so far to display code alongside a rendered example (e.g., <DocsLink slug="reference/components/play-button">PlayButton</DocsLink>).
