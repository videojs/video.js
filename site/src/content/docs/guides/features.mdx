Not every player needs to support every use case. To address this, Video.js has a concept of **features** — self-contained units of player functionality. Each one adds state properties and actions to the player. For example, "playback" adds `paused` and `play()`, "volume" adds `volume` and `setVolume()`, and so on.

<DocsLinkCard slug="reference/api/player-store">See every feature's state and actions</DocsLinkCard>

## Feature bundles and presets

You probably don't want to hand-pick every feature your player needs. A **feature bundle** groups the features needed for a specific use case into a single array.

<FrameworkCase frameworks={["react"]}>

For example, the `/video` preset configures `VideoPlayer` with `videoFeatures`, which bundles playback, volume, time, fullscreen, and more — everything a general video player needs:

```tsx
import { VideoPlayer, Video, VideoSkin } from '@videojs/react/video';

<VideoPlayer>
  <VideoSkin>
    <Video src="movie.mp4" />
  </VideoSkin>
</VideoPlayer>
```

</FrameworkCase>
<FrameworkCase frameworks={["html"]}>

For example, if you import `<video-player>` from the `/video` path, you will have playback, volume, time, fullscreen, and more already enabled.

```html
<script type="module">
  import '@videojs/html/video/player';
  import '@videojs/html/video/skin';
</script> <!-- [!code focus] -->
<video-player> <!-- [!code focus] -->
  <video-skin>
    <video src="movie.mp4"></video>
  </video-skin>
</video-player> <!-- [!code focus] -->
```
</FrameworkCase>

Feature bundles are usually paired with specific skins and media elements in a **preset**. To learn more about this, and the available presets, you'll want to check out the presets guide.

<DocsLinkCard slug="guides/presets">Learn more about presets</DocsLinkCard>

## Individual features
If you're not using presets, you can create a player that has individual features.

<FrameworkCase frameworks={["react"]}>
```tsx
import { createPlayer, playbackFeature, volumeFeature, timeFeature, controlsFeature } from '@videojs/react';

const { Player } = createPlayer({
  features: [playbackFeature, volumeFeature, timeFeature, controlsFeature],
});
```
</FrameworkCase>

<FrameworkCase frameworks={["html"]}>
```ts
import { controlsFeature, createPlayer, playbackFeature, timeFeature, volumeFeature } from '@videojs/html';

const { PlayerElement: MyPlayer } = createPlayer({ // [!code focus]
  features: [playbackFeature, volumeFeature, timeFeature, controlsFeature], // [!code focus]
}); // [!code focus]

customElements.define('my-player', MyPlayer);
```
</FrameworkCase>

## Extended feature bundles

Since feature bundles are just an array of features under the hood, it doesn't take much to extend one. For example, if you were using the `/background` preset and wanted a play button on your background video, you might add the playback feature.

<FrameworkCase frameworks={["react"]}>
```tsx
import { createPlayer, playbackFeature } from '@videojs/react';
import { backgroundFeatures } from '@videojs/react/background';

const { Player } = createPlayer({
  features: [...backgroundFeatures, playbackFeature],
});
```
</FrameworkCase>
<FrameworkCase frameworks={["html"]}>
```ts
import { createPlayer, playbackFeature } from '@videojs/html';
import { backgroundFeatures } from '@videojs/html/background';

const { PlayerElement: MyPlayer } = createPlayer({ // [!code focus]
  features: [...backgroundFeatures, playbackFeature], // [!code focus]
}); // [!code focus]

customElements.define('my-player', MyPlayer);
```
</FrameworkCase>

## Features inside components

<FrameworkCase frameworks={["react"]}>
You access feature state and actions through <DocsLink slug="reference/api/use-player">`usePlayer`</DocsLink>:
```tsx
// Subscribe to state (re-renders when selected values change)
const { paused, volume } = usePlayer((s) => ({
  paused: s.paused,
  volume: s.volume,
}));

// Call actions
const store = usePlayer();
store.play();
store.setVolume(0.8);
```
</FrameworkCase>

<FrameworkCase frameworks={["html"]}>
You can access feature state and actions through <DocsLink slug="reference/api/player-controller">`PlayerController`</DocsLink> and pre-built feature selectors (e.g. <DocsLink slug="reference/api/feature-playback">`selectPlayback`</DocsLink>, <DocsLink slug="reference/api/feature-volume">`selectVolume`</DocsLink>):
```ts
import { selectPlayback } from '@videojs/html';

// Subscribe to feature state (triggers element updates on change)
readonly #playback = new PlayerController(this, selectPlayback);

// Read state and call actions
const media = this.#playback.value;
if (media?.paused) media.play();
```
</FrameworkCase>

<FrameworkCase frameworks={["react"]}>
## Feature selectors
Each feature also has a pre-built selector (e.g. <DocsLink slug="reference/api/feature-playback">`selectPlayback`</DocsLink>, <DocsLink slug="reference/api/feature-volume">`selectVolume`</DocsLink>) that returns just that feature's state and actions:

```tsx
import { selectPlayback, usePlayer } from '@videojs/react';

const playback = usePlayer(selectPlayback);
playback?.play();
```
</FrameworkCase>

## Feature availability

Volume, fullscreen, and picture-in-picture expose availability properties because platform support varies. Volume has two independent properties: `volumeAvailability` for changing the volume level and `mutedAvailability` for toggling mute. For example, iOS Safari allows muting but doesn't allow programmatic volume control.

| Value | Meaning |
|---|---|
| `'available'` | Ready to use |
| `'unavailable'` | Could work, not ready yet |
| `'unsupported'` | Platform can never do this |

<FrameworkCase frameworks={["react"]}>
Components that depend on availability (like <DocsLink slug="reference/components/mute-button">`MuteButton`</DocsLink>, <DocsLink slug="reference/components/pip-button">`PiPButton`</DocsLink>, and <DocsLink slug="reference/components/fullscreen-button">`FullscreenButton`</DocsLink>) handle the three states for you:

- **`unsupported`** — the button returns `null`. No CSS needed.
- **`unavailable`** — the presentation controls stay hidden while capability detection is unresolved. Cast remains visible but disabled when its API is supported and no device is reachable.
- **`disabled` prop** — an available button stays visible and focusable with `aria-disabled="true"` plus `data-disabled` for styling.
- **`available`** — fully interactive.
</FrameworkCase>

<FrameworkCase frameworks={["html"]}>
Components that depend on availability (like <DocsLink slug="reference/components/mute-button">`<media-mute-button>`</DocsLink>, <DocsLink slug="reference/components/pip-button">`<media-pip-button>`</DocsLink>, and <DocsLink slug="reference/components/fullscreen-button">`<media-fullscreen-button>`</DocsLink>) handle the three states for you:

- **`unsupported`** — the element receives the native `hidden` attribute (and `data-hidden`). No CSS needed.
- **`unavailable`** — the presentation controls stay hidden while capability detection is unresolved. Cast remains visible but disabled when its API is supported and no device is reachable.
- **`disabled` attribute** — an available button stays visible and focusable with `aria-disabled="true"` plus `data-disabled` for styling.
- **`available`** — fully interactive.
</FrameworkCase>

Use `data-disabled` to style the non-interactive state:

<FrameworkCase frameworks={["html"]}>
```css
media-pip-button[data-disabled] {
  opacity: 0.5;
  cursor: not-allowed;
}
```
</FrameworkCase>
<FrameworkCase frameworks={["react"]}>
```css
.pip-button[data-disabled] {
  opacity: 0.5;
  cursor: not-allowed;
}
```
</FrameworkCase>

You can also check availability in JS:

<FrameworkCase frameworks={["react"]}>
```tsx title="PiPControl.tsx"
function PiPControl() {
  const availability = usePlayer((s) => s.pictureInPictureAvailability);

  if (availability !== 'available') return null;

  return <PiPButton />;
}
```
</FrameworkCase>
<FrameworkCase frameworks={["html"]}>
```ts
const media = this.#pip.value;

if (media?.pictureInPictureAvailability !== 'available') {
  this.hidden = true;
}
```
</FrameworkCase>
