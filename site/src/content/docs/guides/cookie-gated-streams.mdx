Some CDNs gate a stream with cookies, CloudFront signed cookies for example. When the stream is on another origin, every manifest and segment request has to carry those cookies, or the CDN answers 403.

## Recommended approach

Set the standard `crossorigin="use-credentials"` on the media component:

<FrameworkCase frameworks={["react"]}>
```tsx
<HlsJsVideo src="https://cdn.example.com/stream.m3u8" crossOrigin="use-credentials" />
```
</FrameworkCase>

<FrameworkCase frameworks={["html"]}>
```html
<hlsjs-video src="https://cdn.example.com/stream.m3u8" crossorigin="use-credentials"></hlsjs-video>
```
</FrameworkCase>

Then have the CDN answer with `Access-Control-Allow-Credentials: true` and a specific `Access-Control-Allow-Origin`, not `*`. The browser refuses a credentialed response without both.

## How it works

Under native playback, the browser sends cookies on media requests when the element says `use-credentials`. Streaming engines make their own requests, so the media component reads the same attribute and sets each request's credentials mode to match: `credentials: 'include'` on fetch, `withCredentials` on XHR. Any other value, or no attribute, leaves requests at the default and sends no cross-origin cookies.

On the hls.js components, an `xhrSetup` or `fetchSetup` you pass through `source.engine.hlsJs` still runs, after the credentials mode is set, on the same request.

DRM license requests are separate. See <DocsLink slug="guides/drm" anchor="the-license-request-is-rejected">Play DRM-protected content</DocsLink>.

## Troubleshooting

### Requests still fail with 403

Check that the cookies are set for the CDN's domain and path, and that the request carries them in the browser's network panel. If it doesn't, check the `crossorigin` value on the media component.

### The browser blocks the response with a CORS error

The CDN answered with `Access-Control-Allow-Origin: *` or without `Access-Control-Allow-Credentials: true`. Credentialed requests need both a specific origin and the credentials header.
