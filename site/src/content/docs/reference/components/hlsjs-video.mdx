HLS video element powered by [hls.js](https://github.com/video-dev/hls.js/) for adaptive bitrate streaming, with full feature support across every browser. It's more compatible than the lightweight <DocsLink slug="reference/components/hls-video">HLS video component</DocsLink>, which is smaller and covers most HLS playback. For browser-native playback, see the <DocsLink slug="reference/components/native-hls-video">native HLS video component</DocsLink>.

## Cookie-gated streams

A stream on another origin that is gated by cookies — CloudFront signed cookies, for example — needs those cookies on every manifest and segment request, or the CDN answers 403. Set the standard `crossorigin="use-credentials"` on the element and hls.js sends them (`withCredentials` on its XHR loader, `credentials: 'include'` on its fetch loader), the same way the browser does under native playback. Any other value, or no attribute, leaves hls.js's default and sends no cross-origin cookies. An `xhrSetup` or `fetchSetup` you pass through `source.engine.hlsJs` still runs, after this, on the same request.

The CDN must answer with `Access-Control-Allow-Credentials: true` and a specific `Access-Control-Allow-Origin`, not `*`, or the browser refuses the credentialed response.

<FrameworkCase frameworks={["react"]}>
```tsx
<HlsJsVideo src="https://cdn.example.com/stream.m3u8" crossOrigin="use-credentials" />
```
</FrameworkCase>

<FrameworkCase frameworks={["html"]}>
```html
<hlsjs-video src="https://cdn.example.com/stream.m3u8" crossorigin="use-credentials"></hlsjs-video>
```
</FrameworkCase>

<MediaReference media="HlsJsVideo">
  <Fragment slot="engine-hlsJs">
    Pass hls.js's own configuration here. It's handed to hls.js untouched, so every option in its [config reference](https://github.com/video-dev/hls.js/blob/master/docs/API.md#fine-tuning) works, spelled the way hls.js spells it. <DocsLink slug="guides/media-sources">Media Sources</DocsLink> covers how engine options fit into a structured source.

    The names and types below come from hls.js's own type definitions, so they tell you what exists and what shape it takes. hls.js documents what each one does; the descriptions are theirs to write, and most are blank here because its types carry none.

    <FrameworkCase frameworks={["react"]}>
    ```tsx
    <HlsJsVideo
      source={{
        src: 'https://example.com/playlist.m3u8',
        engine: { hlsJs: { maxBufferLength: 30, lowLatencyMode: true } },
      }}
    />
    ```
    </FrameworkCase>

    <FrameworkCase frameworks={["html"]}>
    ```ts
    const video = document.querySelector('hlsjs-video');
    video.source = {
      src: 'https://example.com/playlist.m3u8',
      engine: { hlsJs: { maxBufferLength: 30, lowLatencyMode: true } },
    };
    ```
    </FrameworkCase>
  </Fragment>
  <Fragment slot="engine-nativeHls">
    When playback falls back to the browser's own HLS, hls.js isn't involved and its options don't apply. This configures that path instead.
  </Fragment>
